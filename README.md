# Agentic RAG

사내 문서를 검색하고, 문서 근거를 바탕으로 질문에 답하는 RAG 프로젝트
LangGraph를 활용해 기본 RAG부터 Multi-Agent RAG까지 단계별로 구현

## 학습 단계

| 단계                 | 구현 목표                                             | 핵심 개념                                              |
| -------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| [Level 1](./level_1/) | 문서 검색 → 답변 생성                                | State, Node, Edge                                      |
| [Level 2](./level_2/) | 검색 결과 평가 → 필요 시 질의 재작성 및 재검색       | Conditional Edge, Loop, Tool Calling                   |
| [Level 3](./level_3/) | Supervisor가 작업을 분배하고 여러 Agent의 결과를 종합 | Orchestrator-Workers, Parallel Execution, Shared State |

## Agent 처리 구조

```text
                  사용자 질문
                      ↓
                 Supervisor
                      ↓
                  질문 분석
                      ↓
               검색 전략 결정
                      ↓
          ┌───────────┼───────────┐
          ↓           ↓           ↓
      Vector DB     RDBMS     Keyword Search
          ↓           ↓           ↓
          └───────────┼───────────┘
                      ↓
                검색 결과 평가
                      ↓
              충분한 정보인가?
                 /         \
               YES          NO
                ↓            ↓
            답변 생성     Query Rewrite
                ↓            ↓
            근거 검증      다시 검색
                ↓
             최종 답변
```

## 문서 전처리 구조

```text
문서 업로드
    ↓
문서 유형 분류
    ↓
Parsing
    ↓
표 및 레이아웃 복원
    ↓
Metadata Extraction
    ↓
Structure-aware Chunking
    ↓
Embedding
    ↓
Vector DB 저장
```

## 폴더 구조

```text
RAG_agent/
├── README.md
├── level_1/    # 기본 RAG
├── level_2/    # 검색 결과 평가 및 자동 재검색
└── level_3/    # Supervisor 기반 Multi-Agent RAG
```

## LLM 사용 구분

### LLM이 필요한 부분

자연어의 의미를 해석하거나 내용을 생성하는 작업에 사용합니다.

| 작업                  | LLM의 역할                                                    |
| --------------------- | ------------------------------------------------------------- |
| 질문 분석, Supervisor | 질문 의도와 조건을 추출하고, 복잡한 질문을 하위 작업으로 분해 |
| 검색 결과 평가        | 검색된 내용으로 질문에 충분히 답할 수 있는지 판단             |
| Query Rewrite         | 근거가 부족할 때 검색 질의를 재작성                           |
| 답변 생성             | 여러 문서의 근거를 종합하고 출처와 함께 답변 작성             |
| 의미 기반 근거 검증   | 답변의 주장이 인용 문서에 의해 뒷받침되는지 확인              |

단순한 질문 분류나 검색 경로 선택은 규칙으로도 처리할 수 있습니다.

### 생성형 LLM이 필요 없는 부분

| 작업                             | 처리 방법                                                                          |
| -------------------------------- | ---------------------------------------------------------------------------------- |
| 문서 업로드, 유형 분류           | 파일 처리 코드, 확장자 및 MIME 검사                                                |
| 텍스트 추출, 표 및 레이아웃 복원 | PDF 파서, OCR, 레이아웃 분석 도구. 복잡한 스캔 문서는 Vision LLM을 선택적으로 사용 |
| 메타데이터 추출, 청킹            | 파일명, 페이지, 제목 등 구조 기반 규칙. 비정형 의미 추출은 LLM을 선택적으로 사용   |
| Embedding                        | 전용 임베딩 모델로 벡터 생성                                                       |
| 저장, 검색, 필터링               | Vector DB, BM25, SQL, 메타데이터 필터                                              |
| Reranking                        | 전용 Cross-Encoder 등으로 검색 후보 재정렬                                         |
| 흐름 제어, 병렬 실행             | LangGraph의 State, Edge, 조건 분기, 재시도 횟수 제한                               |
| 출처 형식 검증                   | 문서 ID, 페이지, 인용 존재 여부를 코드로 검사                                      |

임베딩, OCR, Reranker도 모델을 사용할 수 있지만, 생성형 LLM 호출과는 구분합니다.

## 성능 개선 기법

최적 조합은 문서와 질문에 따라 달라집니다. 아래 조합부터 구현하고, 실제 질문 평가셋으로 답변 정확도, 검색 Recall@k, 지연 시간, 비용을 비교합니다.

- **구조 기반 청킹 + 메타데이터 필터**: 제목, 조항, 표의 맥락을 유지하고 업체명, 문서 버전 등으로 검색 범위를 좁힙니다.
- **Hybrid Search + RRF**: BM25의 정확한 키워드 검색과 벡터의 의미 검색 결과를 결합합니다. [공식 문서](https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview)
- **Reranking**: 검색 후보를 전용 모델로 재정렬하고 관련성이 높은 근거만 답변에 전달합니다. [공식 문서](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval)
- **Contextual Retrieval**: 청크에 문서 맥락을 짧게 덧붙여, 분할 과정에서 사라진 의미를 보완합니다. 색인 시 LLM 비용이 추가됩니다. [공식 설명](https://www.anthropic.com/engineering/contextual-retrieval)
- **조건부 재검색 + 근거 검증**: 근거가 부족할 때만 질의를 재작성하고 재검색합니다. 반복 횟수를 제한하고, 근거가 없는 주장은 제외합니다.
- **선택적 병렬 실행 + 캐싱**: 독립된 검색을 병렬로 수행하고 임베딩, 검색 결과를 캐싱해 지연과 비용을 줄입니다. 복잡한 질문에만 Multi-Agent를 사용합니다.

적용 순서: **Level 1에서 청킹, Hybrid Search, Reranking → Level 2에서 조건부 재검색과 검증 → Level 3에서 작업 분해와 병렬 실행**.

## 입력과 출력

- **입력(Input)**: 시스템에 전달하는 재료입니다. 문서 등록 시에는 파일을, 질문 처리 시에는 질문과 검색 조건을 넣습니다.
- **출력(Output)**: 시스템이 처리한 결과입니다. 문서 등록 시에는 검색 가능한 데이터를, 질문 처리 시에는 답변과 출처를 돌려줍니다.
- **메타데이터**: 문서 ID, 업체명, 페이지, 버전처럼 문서를 구분하거나 검색 범위를 제한하는 부가 정보입니다.
- **청크와 임베딩**: 청크는 검색하기 좋게 나눈 문서 조각이고, 임베딩은 그 조각의 의미를 숫자 벡터로 표현한 것입니다.

| 구분      | 입력                                                  | 출력                                                  |
| --------- | ----------------------------------------------------- | ----------------------------------------------------- |
| 문서 등록 | PDF 등 원본 문서, 문서 ID, 업체명, 버전 등 메타데이터 | 텍스트 청크, 페이지 및 출처 정보, 임베딩, 검색 인덱스 |
| Level 1   | 사용자 질문, 선택적 검색 필터                         | 검색 근거에 기반한 답변, 출처(문서 ID, 페이지)        |
| Level 2   | Level 1과 동일                                        | 답변과 출처, 근거 부족 시 답변 보류 및 사유           |
| Level 3   | 여러 문서 비교 등 복합 질문, 선택적 검색 필터         | 하위 작업 결과를 종합한 답변과 출처, 미해결 항목      |

내부 실행 기록에는 검색 청크와 점수, 재작성 질의, 재검색 횟수, Agent별 결과, 실행 시간, 토큰 사용량을 남깁니다.

예: `“A업체와 B업체의 계약 해지 조건을 비교해줘”` → 업체별 해지 조건 비교표 + 각 계약서의 페이지 출처. 조건을 찾지 못한 업체는 `근거 부족`으로 표시합니다.

## 평가지표

| 평가 대상      | 지표                  | 측정 내용                                                                  |
| -------------- | --------------------- | -------------------------------------------------------------------------- |
| 검색           | Recall@k ↑           | 정답 근거 청크 중 상위 k개 검색 결과에 포함된 비율                         |
| 검색           | Precision@k ↑        | 상위 k개 검색 결과 중 질문에 관련된 청크의 비율                            |
| 답변           | 정답 정확도 ↑        | 기준 답변의 필수 사실을 맞게 포함하고 잘못된 내용을 추가하지 않았는지 평가 |
| 근거           | Faithfulness ↑       | 답변의 주장 중 검색 근거로 뒷받침되는 비율                                 |
| 질문 대응      | Response Relevancy ↑ | 질문이 요구한 내용을 직접 답하고 있는지 평가                               |
| 출처           | 인용 정확도 ↑        | 인용한 문서와 페이지가 연결된 주장을 실제로 뒷받침하는 비율                |
| 근거 부족 대응 | 답변 보류 정확도 ↑   | 답할 수 있는 질문과 근거가 없어 보류해야 하는 질문을 올바르게 구분한 비율  |
| 실행 성능      | 응답 시간, 비용 ↓    | 질문당 전체 실행 시간(p50, p95), 토큰 및 모델 호출 비용                    |

Faithfulness와 Response Relevancy는 [Ragas 공식 지표](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/)를 활용할 수 있습니다. LLM 평가 점수는 사람의 표본 검토로 확인하며, 근거 충실도와 정답 정확도는 따로 측정합니다.

### 지표를 쉽게 이해하기

- **Recall@k**: 필요한 근거를 얼마나 빠짐없이 찾았는지 봅니다. 정답 근거가 4개인데 상위 5개 결과에서 3개를 찾았다면 Recall@5는 75%입니다.
- **Precision@k**: 찾은 결과에 불필요한 내용이 얼마나 적은지 봅니다. 상위 5개 결과 중 관련 청크가 3개라면 Precision@5는 60%입니다. `k`는 평가할 검색 결과 개수입니다.
- **정답 정확도**: 실제 답을 맞혔는지 봅니다. 계약서의 해지 통보 기한이 30일이면 답변도 30일이어야 합니다.
- **Faithfulness(근거 충실도)**: 검색된 문서에 없는 내용을 지어내지 않았는지 봅니다. 잘못된 문서를 충실히 요약할 수도 있으므로 정답 정확도와 함께 확인합니다.
- **Response Relevancy(답변 관련성)**: 질문에 맞는 답을 했는지 봅니다. 해지 조건을 물었는데 계약 금액만 설명하면 낮게 평가합니다.
- **인용 정확도**: 붙인 출처가 해당 설명의 증거인지 봅니다. 페이지가 실제로 존재하더라도 그 페이지에 해지 조건이 없으면 올바른 인용이 아닙니다.
- **답변 보류 정확도**: 근거가 없을 때는 보류하고, 근거가 있을 때는 답하는지 봅니다. 모든 질문에 “모르겠습니다”라고 답해도 좋은 성능은 아닙니다.
- **응답 시간과 비용**: 답변이 얼마나 빠르고 경제적인지 봅니다. p50은 절반의 요청이 완료되는 시간, p95는 95%의 요청이 완료되는 시간입니다. 비용은 질문당 모델 호출과 토큰 사용량 등을 합산합니다.

`↑`는 높을수록, `↓`는 낮을수록 좋다는 뜻입니다. 검색 지표로 **근거를 잘 찾았는지**, 답변 지표로 **근거를 활용해 잘 답했는지**, 실행 지표로 **시간과 비용이 적절한지**를 나누어 확인합니다.

### 레벨별 평가 포인트

- **Level 1**: 정답 근거를 검색하는지, 답변과 출처가 정확한지 확인합니다.
- **Level 2**: 같은 질문에서 재검색 전후 정확도와 근거 회수율이 개선되는지, 추가 시간과 비용이 얼마나 드는지 비교합니다.
- **Level 3**: 복합 질문의 필수 하위 작업을 모두 해결한 비율과 최종 답변 정확도를 확인하고, 순차 실행 대비 병렬 실행 시간을 비교합니다.

평가셋은 `질문, 기준 답변, 정답 근거 청크 ID 및 페이지, 답변 가능 여부`로 구성합니다. 단순 검색, 여러 문서 비교, 문서에 답이 없는 질문을 포함하고, 튜닝용 질문과 최종 평가용 질문을 분리합니다. 같은 문서 버전과 질문으로 레벨별 결과를 비교하며, 청킹이 달라지면 근거 라벨도 다시 매핑합니다.
